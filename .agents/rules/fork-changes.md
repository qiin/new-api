# 二次开发规则（Fork Rules）

本仓库是上游 new-api 的 fork：`main` 只用于同步官方版本，二次开发的改动最终合并进 `production`。
任何改动上游代码的任务都必须遵守本文件，规则的 MUST / 不得 与 `AGENTS.md` 同等效力。

## 变更记录（强制）

- 开始改动前，先用文件读取工具读仓库根目录的 `FORK_CHANGES.md`，了解已有的二次开发改动、分支约定与
  GitHub 协作要求。
- 改完代码后，**必须**在 `FORK_CHANGES.md` 的「四、变更记录」中，按该文档「五、记录模板」追加一条记录，
  并与代码放在**同一个提交**里。只提交代码而不记录，视为任务未完成。
- 记录必须写清楚新增了哪些文件、改动了哪些上游既有文件以及各自改了什么。这一段是日后同步上游新版本、
  解决合并冲突时的主要依据。

## 可持续跟随上游更新（强制）

改动必须做到：上游发布新版本时仍能顺利合并进来，不会因为我们改过代码而合不了。

- 功能逻辑尽量放进**全新文件**，新文件与上游永远不冲突。
- 对上游既有文件只做**追加式的最小改动**：加一行注册、加一个 `case`、加一个分支。
- 不重排、不重构、不顺手修改无关代码行，包括上游既存的 lint 告警与格式问题。
- 不为了统一风格去改动上游既有代码。
- **i18n 语言包（`web/src/i18n/locales/*.json`）新增文案时，必须插进 A-Z 有序区**
  （即 `"Zoom"` 之前），按英文键的字母序就位；**不得追加到文件末尾**。
  末尾那段乱序区是上游自己放新文案的地方，我们也往那里追加，每次同步上游都会撞成一大块冲突。
- 提交前用 `git merge-tree --write-tree <本分支> <上游分支>` 实测一次能否合并；有冲突就调整改动位置，
  不要留给以后的人。
