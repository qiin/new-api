# 二次开发规则（Fork Rules）

本仓库是上游 new-api 的 fork：`main` 只用于同步官方版本，二次开发的改动最终合并进 `production`。
任何改动上游代码的任务都必须遵守本文件，规则的 MUST / 不得 与 `AGENTS.md` 同等效力。

## 分支（强制）

- `main` 是上游的纯镜像，只快进同步，不在上面改业务代码。
- **功能分支从 `production` 切出，不从 `main` 切出**，合回 `production`。
  从 `main` 切出会把官方提交混进功能合并，一次合并同时承载「新功能」和「上游同步」两种变化。
- 同步线（上游 → `main` → `production`）与功能线（`production` → 功能分支 → `production`）
  必须是两次独立的合并，不要混在一起。
- 开新功能前先确认 `production` 已经同步到最新 `main`，再切分支。
- 提交前自检 `git log --oneline origin/production..HEAD`，里面不应该出现官方提交。

## 变更记录（强制）

- 开始改动前，先用文件读取工具读仓库根目录的 `FORK_CHANGES.md`，了解已有的二次开发改动、分支约定与
  GitHub 协作要求。
- 改完代码后，**必须**在 `FORK_CHANGES.md` 的「四、变更记录」中，按该文档「五、记录模板」追加一条记录，
  并与代码放在**同一个提交**里。只提交代码而不记录，视为任务未完成。
- 记录必须写清楚新增了哪些文件、改动了哪些上游既有文件以及各自改了什么。这一段是日后同步上游新版本、
  解决合并冲突时的主要依据。

## 可持续跟随上游更新（强制）

改动必须做到：上游发布新版本时仍能顺利合并进来，不会因为我们改过代码而合不了。

- 功能逻辑尽量放进**全新文件**，新文件与上游永远不冲突。
- 对上游既有文件只做**追加式的最小改动**：加一行注册、加一个 `case`、加一个分支。
- 不重排、不重构、不顺手修改无关代码行，包括上游既存的 lint 告警与格式问题。
- 不为了统一风格去改动上游既有代码。
- **i18n 语言包（`web/src/i18n/locales/*.json`）新增文案时，必须插进 A-Z 有序区**
  （即 `"Zoom"` 之前），按英文键的字母序就位；**不得追加到文件末尾**。
  末尾那段乱序区是上游自己放新文案的地方，我们也往那里追加，每次同步上游都会撞成一大块冲突。
- 提交前用 `git merge-tree --write-tree <本分支> <上游分支>` 实测一次能否合并；有冲突就调整改动位置，
  不要留给以后的人。
- **禁止自作主张同步 `main`。** 同步上游只在仓库所有者明确要求时执行，或者由他本人手动操作。
  发现上游有新版本可以告知，但不要顺手把它合进来，也不要在做别的任务时「顺便」同步。
- 同步上游时**同步到官方版本标签**（`git merge --ff-only v1.0.0-rc.N`），不要跟 `upstream/main` 的
  最新提交。不需要每次官方有提交就同步。
- **绝对不要把标签推到 `origin`**：只用 `git push origin main`，禁止 `--tags` / `--follow-tags`，
  禁止把 `push.followTags` 设为 true。`git fetch upstream --tags` 只写本地，是安全的。
  原因：`docker-build.yml` 与 `release.yml` 的触发条件是 `tags: ['*']`，推上去会逐个触发构建与发版。
- 本仓库的 GitHub Actions 未启用，没有自动 CI 把关，`FORK_CHANGES.md` 第五节第 4 步的
  验证命令必须手动跑完，不得以「应该没问题」代替。
